# ADR 0001: Separate editorial briefing boundary

Status: pilot implementation; external distribution not authorized.

The existing ingestion transaction and live broadcast remain unchanged. Briefings read canonical events and current facts after ingestion, require source rights decisions, and snapshot evidence into immutable briefing revisions. FREE is a national public briefing; PRO is a state/topic-scoped professional draft. Neither suppresses public safety facts as a sales tactic. Both are independent public-source analysis, not government or emergency alerts.

An unknown or expired commercial reuse decision denies inclusion. Rights decisions must be made by a person after reviewing source-specific terms; feed availability does not establish commercial rights. `source_rights_decisions` records the reviewer, terms URL, and expiry; only a conservative, fact-attributed text template is used. No third-party images, article bodies or video are copied. Reassessment, revocation, source corrections and sensitive allegations need a human review path before broader pilot use.

`0004_editorial_briefings.sql` adds drafts, immutable revisions, rights decisions, actions and review outbox. Existing tables, RTMP, automated broadcast and upload settings are not modified. Upgrade is additive and transactionally versioned. Before upgrading an operator-owned database, stop the *new briefing writer* and take a consistent SQLite backup with Python `sqlite3.Connection.backup()` into a private file; verify with `PRAGMA integrity_check`. Recovery means restoring the backup while no writers run, not dropping v4 tables. Existing database migration is automatic on `python main.py newsletter drafts` and other normal commands. The `NEWSROOM_DB` environment override can direct a rehearsal to a copy.

Only a new revision may enqueue a new review notification; the outbox has a unique `(draft_id, revision_id, recipient, kind)` constraint and retry/dead-letter fields. Local fake sending does not contact any mail service. Exactly-once *outbox insertion* is enforced, but a crash after provider acceptance and before receipt storage could produce a second physical email. Gmail send does not offer a per-send idempotency key; use the stable Message-ID and manual sent-mail reconciliation rather than blindly re-sending an ambiguous delivery. Email reply content is untrusted and cannot approve. Threading fields (`message_id`, `in_reply_to`) exist for a later verified inbound bridge, with no inbox OAuth scope now.

Gmail is the selected editorial transport for the pilot, and the owner selected `jarvintels@gmail.com` as both sender and recipient (a choice, not OAuth consent or permission to send). The adapter requests only `https://www.googleapis.com/auth/gmail.send`, uses desktop loopback authorization with PKCE, and stores its separate refresh token in a private `.env`. Required environment variable names are `NEWSROOM_GMAIL_CLIENT_ID`, `NEWSROOM_GMAIL_CLIENT_SECRET`, and `NEWSROOM_GMAIL_REFRESH_TOKEN`; optional `NEWSROOM_GMAIL_SENDER`, if set, must equal `editorial.sender`. They do not reuse YouTube's broader OAuth token. OAuth consent alone never sends email. `editorial.real_mail_enabled` remains false, and real mail additionally requires an interactive, explicitly targeted `newsletter gmail-send-test <draft_id> --revision N --hash SHA256 --execute --confirm-recipient <editorial.to>` invocation. `gmail-send-test` without `--execute` is read-only. Gmail receipts retain `id` and `threadId`; a follow-up revision uses matching subject and RFC `In-Reply-To`/`References`. Unknown network outcomes mark an outbox job `uncertain` rather than automatically retry it; a crash between Gmail acceptance and receipt commit still requires manual sent-mail reconciliation. No inbox access exists with the send-only scope, so the tool cannot automatically resolve that ambiguity or verify sender account identity; Gmail enforces configured send-as identity.

For Gmail setup, the owner chose a separate desktop OAuth client in the existing Google Cloud project. The owner must enable the Gmail API, configure the OAuth consent screen to request `gmail.send`, and add the sender as a test user if the app remains External/Testing. Download the desktop-client JSON to a private path outside the repository, make it mode `0600`, then run `python main.py newsletter gmail-import-client --client-json /absolute/path/to/client.json`. This imports only the Gmail client ID/secret into the existing protected `.env` without replacing the YouTube credentials. It does not grant OAuth or send anything. A separate `python main.py newsletter gmail-auth --authorize` run starts local browser consent and saves the Gmail-only refresh token. An External/Testing project may issue refresh tokens expiring after seven days, so it is not a durable production authorization until the Cloud project's consent status is reviewed.

Approval binds actor, revision, digest and destinations, but the current local OS session check is not sufficient authentication for an internet-facing approval service. Therefore the only allowed approval destination is `mock`, and `editorial.distribution_enabled: false` cannot enable a real send. Adding external distribution requires an authenticated reviewer interface, validation immediately before every send, a distribution outbox, consent/suppression, and explicit operator authorization. No billing, subscriber distribution, or public paid archive exists in this slice.

Paid video must never be a hidden or unlisted MP4 URL. Future protected playback requires an authenticated HTTPS portal, server-side entitlement checks on every resource, short-lived signed grants, encrypted storage, and rights review of media inputs. The existing local preview and public broadcast do not satisfy that trust boundary.

Threats to review before pilot: malicious feed text/HTML, forged editorial replies, stolen desktop session, stale or conflicting evidence, rights changes, duplicate external sends, subscriber PII, and paid media URL leakage. Templates HTML-escape text and default-deny unknown source rights; they do not establish semantic truth. A real editorial process must verify source claims and high-risk legal/safety assertions. No subscriber PII is stored in this slice.
